# Архитектурные решения (ADR)

Формат: Решение · Альтернативы · Причина.

## ADR-0001. Клиент — Tauri + React + TypeScript

- **Альтернативы:** Electron, .NET WPF/WinUI, чистый Web.
- **Причина:** лёгкий бинарник и низкое потребление памяти (важно при 16 GB RAM), доступ к нативным средствам ОС для vision-слоя, единый язык UI (TS). Требует Rust + MSVC (установлены).

## ADR-0002. Серверные сервисы — Python + FastAPI

- **Альтернативы:** Node/TypeScript (единый с клиентом), Go.
- **Причина:** опыт владельца (проект `gl-jb`), бесплатный стек, богатая экосистема для LLM/ML и быстрая разработка. Единый язык с клиентом не критичен.

## ADR-0003. Модели — облачные free LLM + локальный Ollama fallback

- **Альтернативы:** только облако (дорого/риск), только локально (слабые 8 GB VRAM).
- **Причина:** заказчик использует free-агентов; локальный `qwen3.5:9b` (vision/tools) — fallback и приватный режим. Маршрутизация по типу задачи через LLM Gateway.

## ADR-0004. Интеграция — vision-агент (наблюдение за экраном)

- **Альтернативы:** API-подключение, парсинг/selenium, OCR внешних страниц.
- **Причина:** прямые интеграции запрещены ToS площадок (см. audit-report §3). Владелец выбрал модель «агент видит экран, не подключается и не парсит сайт». Правовая проверка проведена владельцем.

## ADR-0005. Психопрофиль собеседника — только пользователю

- **Причина:** снижение риска «диагнозов» и вреда; агент общается **в стиле пользователя**, а аналитика отображается лишь владельцу.

## ADR-0006. LLM работает по строго прописанным сценариям

- **Причина:** защита от prompt injection и от неограниченных действий. Входящие сообщения — недоверенный ввод; allowlist инструментов; отделение анализа от разрешений.

## ADR-0007. Данные — без персональных данных, доступ по токенам

- **Причина:** минимизация правовых обязательств (GDPR/локальные). Секреты и персональные данные в БД не хранятся.

## ADR-0008. Захват экрана — Windows.Graphics.Capture

- **Альтернативы:** нативный Rust-хук, периодические снимки по триггеру.
- **Причина:** владелец выбрал `Windows.Graphics.Capture` — современный стабильный API Windows, корректно работает с окнами/экраном и дружелюбен к Tauri/WebView2. Реализуется в Rust-части Tauri (Этап 5).

## ADR-0009. Автономия на старте — авто-отправка

- **Альтернативы:** черновики (пользователь отправляет сам), ручное подтверждение.
- **Причина:** владелец выбрал авто-отправку ответов агентом на первом релизе; пользователь наблюдает. Требует строгих сценариев и allowlist инструментов (ADR-0006) как компенсация риска.

## ADR-0010. Промежуточная токен-авторизация (Этап 2)

- **Альтернативы:** JWT-сессии, OAuth/OIDC, полноценный реестр токенов с отзывом.
- **Причина:** OQ-7 ещё не закрыт; чтобы разблокировать Этап 2, введена минимальная схема: токен передаётся в `Authorization: Bearer <token>` или `X-Match-Token`, `token_ref` хранится в `users` (без персональных данных), при первом обращении пользователь создаётся автоматически. Схема временная: финализация (генерация/ротация/отзыв) — Этап 9. Автопровижининг и изоляция по пользователю проверены тестами.

## ADR-0011. Промежуточный LLM-слой (Этап 3)

- **Альтернативы:** сразу полноценный LLM Gateway с маршрутизацией/лимитами (Этап 6).
- **Причина:** Dialogue Engine нужен провайдер уже на Этапе 3. Введён минимальный интерфейс `LLMProvider` (`app/llm/`) с двумя реализациями: `EchoProvider` (детерминированный, по умолчанию — оффлайн и в тестах) и `OllamaProvider` (локальный Ollama). Выбор — через `MATCH_LLM_PROVIDER`. Клиент облачных free LLM, маршрутизация, fallback и лимиты — Этап 6 (OQ-2).

## ADR-0012. Оценки Trust/Compatibility — детерминированные эвристики (Этап 4)

- **Альтернативы:** LLM-анализ сразу.
- **Причина:** на Этапе 4 нужны раздельные и объяснимые показатели риск/взаимность/совместимость без зависимости от ещё не выбранных провайдеров (OQ-2). Реализованы правила: `app/trust/engine.py` (сигналы риска по категориям, severity, рекомендованное действие) и `app/compatibility/engine.py` (Jaccard-совместимость целей/ценностей, совпадение lifestyle, взаимность по балансу сообщений, `uncertainty` по полноте данных). `model_version=heuristic-1.0`; LLM-уточнение — позже, версия фиксируется в записи.

## ADR-0013. LLM Gateway: провайдеры, fallback, лимиты (Этап 6)

- **Альтернативы:** жёстко один провайдер; внешний роутер.
- **Причина:** OQ-2 не закрыт, нужна свобода выбора провайдеров. Реализовано: интерфейс `LLMProvider` с реализациями `EchoProvider` (оффлайн), `OllamaProvider` (локальный), `OpenAICompatProvider` (любой OpenAI-совместимый облачный API). Порядок — `MATCH_LLM_PROVIDER` + `MATCH_LLM_FALLBACK_PROVIDERS`; при ошибке/пустом ответе — переход к следующему; если все недоступны — `LLMUnavailable` (HTTP 503). Учёт запусков в `model_runs`; per-user лимит `MATCH_LLM_USER_REQUEST_LIMIT` (0 = без лимита, HTTP 429). Конкретные облачные провайдеры и политика лимитов — по OQ-2.

## ADR-0014. Интеграции: ручной импорт + явный `unsupported` (Этап 7)

- **Альтернативы:** прямые коннекторы к площадкам; имитация подключения для «красивого» UI.
- **Причина:** агент не подключается к площадкам напрямую (ADR-0004/ADR-0008) — он наблюдает экран. Поэтому единственная разрешённая интеграция — ручной импорт сообщений; всё остальное честно помечается `unsupported` вместо имитации (roadmap, Этап 7). Введён контракт `IntegrationAdapter` (`app/integrations/base.py`: `platform_id`, `display_name`, `capabilities`, `status()`, `disconnect()`), реестр площадок (`registry.py`) и адаптеры `ManualImportAdapter` (поддержан) и `UnsupportedAdapter` (Tinder, Badoo, Bumble, OkCupid, Hinge, Мамба). API: `GET /api/v1/integrations`, `GET /{platform_id}/capabilities`, `GET /{platform_id}/status`, `POST /{platform_id}/disconnect` (для `unsupported` — `409`). Contract-тесты (`tests/test_integrations.py`) проверяют, что каждый адаптер удовлетворяет контракту. `disconnect` для ручного импорта — осознанный no-op (реального подключения нет). Прямые подключения к площадкам возможны только при повторной юридической проверке и отдельном ADR.
