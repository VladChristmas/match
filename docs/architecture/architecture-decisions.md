# Архитектурные решения (ADR)

Формат: Решение · Альтернативы · Причина.

## ADR-0001. Клиент — Tauri + React + TypeScript

- **Альтернативы:** Electron, .NET WPF/WinUI, чистый Web.
- **Причина:** лёгкий бинарник и низкое потребление памяти (важно при 16 GB RAM), доступ к нативным средствам ОС для vision-слоя, единый язык UI (TS). Требует Rust + MSVC (установлены).

## ADR-0002. Серверные сервисы — Python + FastAPI

- **Альтернативы:** Node/TypeScript (единый с клиентом), Go.
- **Причина:** опыт владельца (проект `gl-jb`), бесплатный стек, богатая экосистема для LLM/ML и быстрая разработка. Единый язык с клиентом не критичен.

## ADR-0003. Модели — облачные free LLM + локальный Ollama fallback

- **Альтернативы:** только облако (дорого/риск), только локально (слабые 8 GB VRAM).
- **Причина:** заказчик использует free-агентов; локальный `qwen3.5:9b` (vision/tools) — fallback и приватный режим. Маршрутизация по типу задачи через LLM Gateway.

## ADR-0004. Интеграция — vision-агент (наблюдение за экраном)

- **Альтернативы:** API-подключение, парсинг/selenium, OCR внешних страниц.
- **Причина:** прямые интеграции запрещены ToS площадок (см. audit-report §3). Владелец выбрал модель «агент видит экран, не подключается и не парсит сайт». Правовая проверка проведена владельцем.

## ADR-0005. Психопрофиль собеседника — только пользователю

- **Причина:** снижение риска «диагнозов» и вреда; агент общается **в стиле пользователя**, а аналитика отображается лишь владельцу.

## ADR-0006. LLM работает по строго прописанным сценариям

- **Причина:** защита от prompt injection и от неограниченных действий. Входящие сообщения — недоверенный ввод; allowlist инструментов; отделение анализа от разрешений.

## ADR-0007. Данные — без персональных данных, доступ по токенам

- **Причина:** минимизация правовых обязательств (GDPR/локальные). Секреты и персональные данные в БД не хранятся.

## ADR-0008. Захват экрана — Windows.Graphics.Capture

- **Альтернативы:** нативный Rust-хук, периодические снимки по триггеру.
- **Причина:** владелец выбрал `Windows.Graphics.Capture` — современный стабильный API Windows, корректно работает с окнами/экраном и дружелюбен к Tauri/WebView2. Реализуется в Rust-части Tauri (Этап 5).

## ADR-0009. Автономия на старте — авто-отправка

- **Альтернативы:** черновики (пользователь отправляет сам), ручное подтверждение.
- **Причина:** владелец выбрал авто-отправку ответов агентом на первом релизе; пользователь наблюдает. Требует строгих сценариев и allowlist инструментов (ADR-0006) как компенсация риска.

## ADR-0010. Промежуточная токен-авторизация (Этап 2)

- **Альтернативы:** JWT-сессии, OAuth/OIDC, полноценный реестр токенов с отзывом.
- **Причина:** OQ-7 ещё не закрыт; чтобы разблокировать Этап 2, введена минимальная схема: токен передаётся в `Authorization: Bearer <token>` или `X-Match-Token`, `token_ref` хранится в `users` (без персональных данных), при первом обращении пользователь создаётся автоматически. Схема временная: финализация (генерация/ротация/отзыв) — Этап 9. Автопровижининг и изоляция по пользователю проверены тестами.

## ADR-0011. Промежуточный LLM-слой (Этап 3)

- **Альтернативы:** сразу полноценный LLM Gateway с маршрутизацией/лимитами (Этап 6).
- **Причина:** Dialogue Engine нужен провайдер уже на Этапе 3. Введён минимальный интерфейс `LLMProvider` (`app/llm/`) с двумя реализациями: `EchoProvider` (детерминированный, по умолчанию — оффлайн и в тестах) и `OllamaProvider` (локальный Ollama). Выбор — через `MATCH_LLM_PROVIDER`. Клиент облачных free LLM, маршрутизация, fallback и лимиты — Этап 6 (OQ-2).

## ADR-0012. Оценки Trust/Compatibility — детерминированные эвристики (Этап 4)

- **Альтернативы:** LLM-анализ сразу.
- **Причина:** на Этапе 4 нужны раздельные и объяснимые показатели риск/взаимность/совместимость без зависимости от ещё не выбранных провайдеров (OQ-2). Реализованы правила: `app/trust/engine.py` (сигналы риска по категориям, severity, рекомендованное действие) и `app/compatibility/engine.py` (Jaccard-совместимость целей/ценностей, совпадение lifestyle, взаимность по балансу сообщений, `uncertainty` по полноте данных). `model_version=heuristic-1.0`; LLM-уточнение — позже, версия фиксируется в записи.

## ADR-0013. LLM Gateway: провайдеры, fallback, лимиты (Этап 6)

- **Альтернативы:** жёстко один провайдер; внешний роутер.
- **Причина:** OQ-2 не закрыт, нужна свобода выбора провайдеров. Реализовано: интерфейс `LLMProvider` с реализациями `EchoProvider` (оффлайн), `OllamaProvider` (локальный), `OpenAICompatProvider` (любой OpenAI-совместимый облачный API). Порядок — `MATCH_LLM_PROVIDER` + `MATCH_LLM_FALLBACK_PROVIDERS`; при ошибке/пустом ответе — переход к следующему; если все недоступны — `LLMUnavailable` (HTTP 503). Учёт запусков в `model_runs`; per-user лимит `MATCH_LLM_USER_REQUEST_LIMIT` (0 = без лимита, HTTP 429). Конкретные облачные провайдеры и политика лимитов — по OQ-2.

## ADR-0014. Интеграции: ручной импорт + явный `unsupported` (Этап 7)

- **Альтернативы:** прямые коннекторы к площадкам; имитация подключения для «красивого» UI.
- **Причина:** агент не подключается к площадкам напрямую (ADR-0004/ADR-0008) — он наблюдает экран. Поэтому единственная разрешённая интеграция — ручной импорт сообщений; всё остальное честно помечается `unsupported` вместо имитации (roadmap, Этап 7). Введён контракт `IntegrationAdapter` (`app/integrations/base.py`: `platform_id`, `display_name`, `capabilities`, `status()`, `disconnect()`), реестр площадок (`registry.py`) и адаптеры `ManualImportAdapter` (поддержан) и `UnsupportedAdapter` (Tinder, Badoo, Bumble, OkCupid, Hinge, Мамба). API: `GET /api/v1/integrations`, `GET /{platform_id}/capabilities`, `GET /{platform_id}/status`, `POST /{platform_id}/disconnect` (для `unsupported` — `409`). Contract-тесты (`tests/test_integrations.py`) проверяют, что каждый адаптер удовлетворяет контракту. `disconnect` для ручного импорта — осознанный no-op (реального подключения нет). Прямые подключения к площадкам возможны только при повторной юридической проверке и отдельном ADR.

## ADR-0015. Автономность: очередь действий и идемпотентность (Этап 8)

- **Альтернативы:** внешний воркер (Celery/RQ/Redis) сразу; синхронная отправка без очереди.
- **Причина:** авто-отправка (ADR-0009) на старте, но нужен предохранитель и передача человеку. Введена in-process очередь — таблица `agent_actions` со статусами `pending` / `sent` / `rejected` и счётчиком попыток (`app/agent/service.py`). Идемпотентность — заголовок `Idempotency-Key` (уникален в рамках пользователя; повторный запрос возвращает существующее действие, `200` вместо `201`). Режим `auto_send` (и отсутствие общей паузы) доставляет сразу: создаётся исходящее `Message` с `source=agent`; иные режимы (`suggest`/`manual`/`paused`) и общая пауза переводят действие в `pending`, где решение принимает человек (`approve` → доставка, `reject` → отказ) — это «передача человеку». Общая пауза — `agent_settings.queue_paused` (`POST /api/v1/agent/pause` / `resume`). API: `GET|PATCH /api/v1/agent/settings`, `GET|POST /api/v1/agent/actions`, `POST /api/v1/agent/actions/{id}/approve|reject`. «Доставка» = импорт исходящего сообщения (реальный канал — интеграции, Этап 7). Внешний воркер, ретраи и реальная отправка на площадку — позже (при закрытии OQ/ADR по интеграциям).

## ADR-0016. Предрелиз: экспорт/удаление данных и ограничение нагрузки (Этап 9)

- **Альтернативы:** отложить приватность и лимиты за релиз; полагаться только на FK-каскад СУБД.
- **Причина:** релиз требует контролируемых приватности, нагрузки и восстановления. Реализовано: `GET /api/v1/privacy/export` — полный экспорт данных пользователя одним JSON (`token_ref` редактируется; персональных данных сверх созданного нет) и `POST /api/v1/privacy/deletion-request` — удаление всех данных пользователя с явным порядком удаления (не полагается на FK-каскад, работает и на SQLite в тестах). Ограничение нагрузки — in-process скользящее окно по пользователю (`app/api/ratelimit.py`), конфиг `MATCH_RATE_LIMIT_PER_MINUTE` (0 = выключено), применяется к `/drafts` и `/agent/actions` (`429`). Инструкция, чек-лист и план отката — `docs/release/`. Инструменты модели ограничены allowlist (ADR-0006): прямые действия — только через `agent-runtime`/очередь. Внешний лимитер (Redis) и автоматическое резервное копирование — при масштабировании.

## ADR-0017. Vision-слой клиента: захват окна и приём кадров (Этап 10)

- **Альтернативы:** парсинг DOM/страниц площадок; периодическая запись видео; облачный скриншот-сервис.
- **Причина:** реализует выбранный подход ADR-0008 (агент видит экран, а не парсит сайт). Клиент (`apps/desktop`, Rust) через `Windows.Graphics.Capture` (крейт `windows`) перечисляет видимые окна и по команде пользователя снимает кадр выбранного окна, отдавая PNG (base64) в интерфейс. Сервер (`POST /api/v1/vision/observations`) принимает кадр, проверяет, что это PNG в пределах лимита, и **не сохраняет изображение**: он пишет только метаданные наблюдения (размеры, размер в байтах, SHA-256, метка источника, время) в таблицу `vision_observations`. Обрезание/уменьшение кадра до 1280 px по ширине выполняется на клиенте. Парсинг чужих сайтов не выполняется, токены площадок не запрашиваются. Анализ кадра мультимодальной моделью отложен до OQ-8, поэтому `analysis_pending=True`.

## ADR-0018. Анализ кадров vision-слоя (Этап 11)

- **Альтернативы:** сразу зафиксировать одного облачного вендора; хранить кадры для повторного анализа; делать анализ отдельным асинхронным воркером.
- **Причина:** продолжает Этап 10 и повторяет паттерн LLM Gateway (ADR-0013). Введён `VisionProvider` (`app/vision/base.py`) и `VisionGateway` (`app/vision/gateway.py`): порядок провайдеров + fallback, `VisionUnavailable`. Провайдеры: `OllamaVisionProvider` (локальный, по умолчанию) и `OpenAICompatVisionProvider` (облако, включается только при заданном ключе — кадры не уходят наружу по умолчанию). Анализ выполняется при приёме кадра; результат пишется в само наблюдение (`summary`, `provider`, `model`, `analysis_pending=False`) и в `ModelRun` (`task_type=vision_observation`), с общим per-user лимитом запросов. Изображение по-прежнему не сохраняется, поэтому повторный анализ без повторной отправки кадра невозможен — при недоступной модели наблюдение сохраняется с `analysis_pending=True`. Конкретная модель — открытый OQ-8 (выбирается настройкой `MATCH_VISION_MODEL`).

## ADR-0019. Пользовательские токены доступа (Этап 12, OQ-7)

- **Альтернативы:** оставить только `token_ref` с автопровижинингом; хранить токены в открытом виде; JWT со сроком жизни и refresh-токенами; внешний провайдер идентичности (OAuth).
- **Причина:** закрывает OQ-7 и заменяет временную схему ADR-0010 на управляемые токены. Токен генерируется сервером (`secrets.token_urlsafe(32)`, префикс `match_`), наружу отдаётся один раз при выдаче, в БД (`access_tokens`) хранится только SHA-256 хэш — при утечке дампа токены не восстанавливаются. Реализованы `POST /api/v1/tokens` (выдача), `GET /api/v1/tokens` (список без секретов), `POST /api/v1/tokens/{id}/rotate` (отзыв старого + выдача новой пары) и `DELETE /api/v1/tokens/{id}` (отзыв); все операции ограничены владельцем. Проверка токена выполняется первым шагом в `get_current_user`, до легаси-пути. Легаси-схема `token_ref` сохранена для разработки и отключается настройкой `MATCH_AUTH_ALLOW_LEGACY_TOKENS=false`; отозванный или неизвестный выданный токен никогда не попадает в легаси-путь (`is_known_token`). JWT и внешний провайдер отклонены как избыточные для локального/одиночного развёртывания и как противоречащие ADR-0007 (минимум персональных данных). Экспорт приватности отдаёт метаданные токенов без хэша, удаление аккаунта удаляет токены.

## ADR-0020. Масштабируемый лимитер нагрузки на БД (Этап 14)

- **Альтернативы:** оставить только in-process лимитер (ADR-0016); поднять Redis; вынести лимит в обратный прокси (nginx/ingress); использовать лимит на уровне облачного провайдера.
- **Причина:** продолжает ADR-0016 и снимает ограничение «один инстанс». Лимитер получил два бэкенда, переключаемых `MATCH_RATE_LIMIT_BACKEND`: `memory` (по умолчанию, in-process скользящее окно — как раньше) и `db` (таблица `rate_limit_counters`, фиксированные окна по 60 с, ключ — id пользователя). Выбран вариант без новой инфраструктуры: Redis отклонён как ещё одна обязательная служба для одиночного развёртывания, а прокси не знает пользователя (ключ лимита — пользователь, не IP). Инкремент счётчика устойчив к гонкам: вставка в SAVEPOINT с обработкой `IntegrityError` и последующим `UPDATE` (без диалект-специфичного `ON CONFLICT`, чтобы работали и PostgreSQL, и SQLite в тестах). Устаревшие окна пользователя удаляются в том же запросе, поэтому таблица не растёт. Отклонённые (429) запросы не инкрементируют счётчик; при одновременных запросах допускается небольшое превышение лимита. Счётчики — служебные данные без содержимого: в экспорт приватности не входят, при удалении аккаунта удаляются.

## ADR-0021. Кабинет суперадмина и роль `admin` (Этап 15, OQ-3)

- **Альтернативы:** отдельная админ-панель/сервис; внешняя аналитика (Prometheus + Grafana); доступ по отдельному админ-токену в заголовке; выдача полного доступа к данным пользователей.
- **Причина:** закрывает OQ-3 минимальными средствами. Роль хранится в `users.role` (миграция `0011_user_role`, по умолчанию `user`), администраторы задаются списком `token_ref` в `MATCH_ADMIN_TOKEN_REFS` и повышаются автоматически при первом запросе (`maybe_promote_admin` в `app/admin/service.py`). Это позволило не вводить отдельный секрет/токен и не плодить вторую схему авторизации, сохранив единый механизм аутентификации (ADR-0010/ADR-0019). Отдельный сервис админки и Prometheus/Grafana отклонены как избыточные для текущего масштаба; вместо них — `GET /api/v1/admin/metrics` (агрегированные счётчики) и `GET /api/v1/admin/whoami`, оба под зависимостью `AdminUser` (403 для остальных). Метрики содержат только количества по категориям (пользователи, диалоги, сообщения, запуски моделей по задаче и провайдеру, наблюдения vision по провайдеру, действия агента, отзывы, токены) и сводку несекретных настроек; персональный профиль и тексты сообщений недоступны и суперадмину — это прямо следует из ADR-0007 (минимум персональных данных) и проверяется тестом на отсутствие содержимого в ответе. Клиент показывает раздел «Админ»; при отсутствии прав выводится объяснение 403.

## ADR-0022. Локальное хранилище клиента на SQLite (Этап 16, OQ-6)

- **Альтернативы:** остаться на `localStorage`/`settings.json`; отдельная облачная синхронизация; IndexedDB в webview; внешняя СУБД на клиенте.
- **Причина:** закрывает OQ-6. Настройки клиента и журнал событий переведены в SQLite-файл `match.db` в каталоге данных приложения (`rusqlite` с `bundled` — SQLite собирается вместе с приложением, внешних зависимостей нет). `localStorage` отклонён как неподходящий для растущего журнала (нет индексов, лимиты объёма, синхронный API), а журнал в одном JSON-блобе перезаписывался целиком при каждом событии. Схема: `settings (key, value)` и `journal (id, at, kind, summary, detail)` с индексом по времени; версия схемы хранится в `PRAGMA user_version`, поэтому новые изменения добавляются ветвью в `migrate` без миграционных инструментов. Запись журнала идемпотентна по `id` (`INSERT OR REPLACE` — повторный вызов в dev-режиме не дублирует записи), история подрезается до 500 записей, настройки сохраняются без блоба журнала. Прежний `settings.json` переносится в БД однократно и переименовывается в `settings.json.migrated`, поэтому данные не теряются при обновлении. Облачная синхронизация и IndexedDB отклонены: данные остаются на устройстве (ADR-0007), а webview-хранилище не даёт файла, который пользователь может удалить. Оффлайн-очередь отправки в этом этапе не реализуется — журнал остаётся журналом операций (OQ-6 закрыт в части «есть ли локальное хранилище»). В браузерном режиме разработки клиент по-прежнему использует `localStorage`, поэтому UI работает и без Tauri.
