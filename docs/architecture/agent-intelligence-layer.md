# Match Agent Intelligence Layer (спецификация поведения)

**Статус:** Draft / на согласовании. Код по этому документу не пишется, пока поведенческая
модель не согласована и не проверена на сквозных сценариях (§11).
**Связь:** надстройка над уже реализованными компонентами (`psychology`/`dialogue`/`trust`/
`compatibility`, память, контроллер автономности, журнал). Новые экраны и отдельные ИИ-модули
не вводятся.

## 0. Назначение

Слой связывает существующие движки в одного агента с замкнутым циклом:

```
Понимает ситуацию → Принимает решение → Проверяет и действует → Оценивает результат
        ▲                                                                    │
        └──────────────── обновлённое понимание ситуации ◀───────────────────┘
```

Слой описывает **контракты и поведенческие правила**, а не новые пользовательские экраны.
Существующие движки остаются владельцами своих данных; слой только оркеструет решения.

## 1. Место в архитектуре и текущие пробелы

`docs/architecture/target-architecture.md` уже объявляет `modules/*` (`psychology·dialogue·trust·
compatibility·memory·audit-log`) и `policy-engine` как часть `agent-runtime`. Фактически:

- Реализовано: `app/dialogue/` (генерация/валидация), `app/trust/engine.py`,
  `app/compatibility/engine.py`, `app/agent/service.py` (очередь, `should_auto_send`),
  `app/agent/worker.py` (отложенная доставка), `user_feedback` (сбор обратной связи).
- Не реализовано как отдельный слой: единая модель состояния агента, формальный выбор из
  альтернатив, жизненный цикл памяти, динамика отношений во времени, бюджеты автономности,
  калибровка на обратной связи. `modules/` и `packages/` содержат только `README.md`.

Этот слой закрывает пробел **не порождая новых сущностей-дубликатов**: он задаёт, как
существующие оценки (`trust`, `compatibility`, стиль, память, разрешения) превращаются в
одно объяснимое действие (или осознанное бездействие).

## 2. Модель состояния агента (AgentState)

Единый снимок, из которого принимается решение. Не хранится целиком; собирается из источников.

| Часть состояния | Источник | Владелец данных |
|---|---|---|
| Профиль и цели пользователя | `user_profiles` | `profile` |
| Стиль общения | `communication_profiles` | `dialogue` |
| Границы и разрешения | `user_profiles.boundaries`, `agent_settings`, `conversations.autonomy_mode` | `agent` |
| Воспоминания (факты/предпочтения/гипотезы) | новая `memories` (§5) | `memory` |
| Динамика отношений (временные ряды) | новая `relationship_signals` (§6) | `dynamics` |
| Риск | `risk_assessments` | `trust` |
| Совместимость/взаимность | `compatibility_assessments` | `compatibility` |
| Бюджеты автономности | `agent_settings` + `autonomy_budgets` (§7) | `agent` |

Снимок материализуется в момент решения и **не кэшируется между запросами**: каждое решение
видит актуальные данные. Версионирование (`context_version`, `profile_version`,
`model_version`) сохраняется в записи решения для воспроизводимости.

## 3. Match Decision Loop

Шесть шагов; каждый сохраняется в `agent_decisions` (§9) с обоснованием.

1. **Восприятие.** Что произошло: новое сообщение, изменение тона, пауза, обратная связь,
   новое свидетельство из памяти/динамики. Входящий текст — недоверенный ввод (ADR-0006).
2. **Состояние.** Сборка `AgentState` (§2) с указанием, каких данных не хватает.
3. **Варианты.** Кандидаты действий, включая **бездействие**. Минимальный набор:
   ответить · уточнить · задать встречный вопрос · подождать · предложить встречу ·
   передать решение пользователю. Набор расширяемый, но каждый вариант должен быть
   выразим через разрешённые типы действий.
4. **Оценка.** Каждый вариант оценивается по осям: соответствие целям, естественность
   (стиль), взаимность, риск. Оценка — **сравнительная**, не единый «магический балл».
5. **Контроль.** Жёсткие проверки: разрешено ли действие, достаточно ли уверенности,
   не нарушаются ли границы, не сработал ли стоп-фактор (§7, §8).
6. **Результат.** Что произошло после действия; нужно ли пересмотреть стратегию.
   Результат попадает в память об опыте (§5.5) и влияет на следующее решение.

Контракт решения:

```
Decision {
  action:        send_message | ask_clarifying | ask_question | wait |
                 propose_meeting | escalate_to_user | no_op
  text:          str | null
  alternatives:  [{action, score, rejected_because}]
  rationale:     str            # почему выбран именно этот вариант/пауза
  confidence:    float          # 0..1, по осям, не агрегат
  evidence:      [memory_id, signal_id, assessment_id]
  permissions:   {allowed: bool, mode: Выполнить|Проверить|Передать|Стоп}
  escalation:    null | {reason}
}
```

**Правило:** при одинаковом `AgentState` и настройках решение стабильно, даже если
формулировка входящего сообщения меняется (инвариант §11).

## 4. Политика действий (обязательные правила)

1. **Цель ≠ манипуляция.** Нельзя максимизировать интерес собеседника любой ценой.
2. **Бездействие — полноценный вариант.** Пауза может быть лучше ещё одного сообщения.
3. **Неопределённость влияет на решение.** Меньше достоверных данных → осторожнее действие.
4. **Жёсткие ограничения важнее оценки выгоды.** Запрет/отсутствие разрешения нельзя
   компенсировать высоким прогнозируемым результатом. Уверенность модели и разрешение —
   **две разные проверки**.
5. **Результат ≠ мгновенная реакция.** Быстрый ответ не доказывает совместимость,
   задержка не доказывает отсутствие интереса.

## 5. Долгосрочная память: изменяемая модель понимания

Не архив переписок, а набор типизированных, пересматриваемых записей.

### 5.1 Пять типов памяти

1. **Устойчивая** — ценности, жизненные цели, неизменяемые без подтверждения факты.
2. **Стиль общения** — как пользователь выражает симпатию/юмор/несогласие; что редактирует.
3. **Знакомство** — история важных событий, интересы, темы, договорённости, нерешённые вопросы.
   Данные одного знакомства **не смешиваются** с другим (изоляция по `conversation_id`/`match_id`).
4. **Гипотезы** — «возможно, важна взаимная инициатива». Хранятся **отдельно** от
   подтверждённых предпочтений, с основаниями; могут быть опровергнуты.
5. **Опыт агента** — какие ответы принимали/исправляли/отменяли и где агент ошибался.

### 5.2 Жизненный цикл воспоминания

`Получено → Классифицировано → Проверено → Используется → Пересмотрено`.

- **Получено:** источник (сообщение/анкета/обратная связь), дата.
- **Классифицировано:** факт / предпочтение / гипотеза / временное состояние / договорённость.
- **Проверено:** достоверность, актуальность, противоречия, чувствительность.
- **Используется:** влияет на решение только в подходящем контексте.
- **Пересмотрено:** новое свидетельство подтверждает/уточняет/опровергает вывод.

### 5.3 Обязательные атрибуты записи

источник · дата · уровень уверенности · срок актуальности (если применим) · история изменений ·
возможность исправления пользователем · правила удаления и ограничения использования.

### 5.4 Контекстная модель, а не ярлык

Пример: пользователь часто просит короче → гипотеза «комфортнее лаконично»; позже в важных
разговорах выбирает развёрнутые ответы → **не** механически сокращать всё, а уточнить модель:
повседневное — коротко, важное — подробнее, при сомнении — естественный вариант по контексту.

### 5.5 Ограничение

Слой **не** превращает любое поведение в постоянную черту личности. Плохое настроение, одна
эмоциональная реакция, неудачное свидание — недостаточные основания для устойчивого вывода.
Противоречивые/устаревшие сведения не используются как бесспорные факты (инвариант §11).

## 6. Динамика отношений (Relationship Dynamics)

Анализ **траектории**, а не отдельных сообщений. Совместимость/взаимность остаётся у
`compatibility`; слой добавляет временной ряд и сравнение периодов.

### 6.1 Измерения (не сворачивать в один балл)

Взаимность · Последовательность (слова↔намерения↔поведение) · Эмоциональный комфорт
(самооценка пользователя) · Совместимость ожиданий · Способность договариваться · Развитие
знакомства. Часть измерений — наблюдаемые, часть — субъективные, часть — неизвестны до встречи.

### 6.2 Обнаружение значимых изменений

При изменении относительно предыдущего периода слой:

1. замечает изменение;
2. проверяет достаточность наблюдений и альтернативные объяснения;
3. показывает, что именно изменилось;
4. отделяет **факты** от интерпретаций;
5. предлагает следующий шаг по целям пользователя.

Запрещено сразу заявлять «интерес пропал». Пример корректной формулировки — в исходном
предложении; шаг обязан ссылаться на `relationship_signals`, а не на одно сообщение.

### 6.3 Журнал поворотных моментов

Вместо длинного отчёта — временная линия значимых событий (совпадение целей, расхождение
ожиданий, обозначенная граница, договорённость о встрече, смена характера инициативы,
пересмотр оценки партнёра). Позволяет объяснить, почему рекомендация сегодня отличается от
рекомендации неделю назад.

### 6.4 Проверка гипотез (без манипуляции)

Никаких скрытых проверок человека и провокаций ревности. Только естественный уточняющий
вопрос либо явное «данных пока недостаточно».

## 7. Управление автономностью

Уровень автономности остаётся **настройкой пользователя**; слой дополнительно определяет,
насколько безопасно конкретное действие **сейчас**.

### 7.1 Четыре режима

| Режим | Когда | Поведение |
|---|---|---|
| **Выполнить** | предусмотрено разрешениями, ситуация знакомая, фактов достаточно, риск низкий | отправить обычный ответ |
| **Подготовить и проверить** | ситуация новая/неоднозначная | подготовить, проверить факты и ограничения, при необходимости запросить подтверждение |
| **Передать пользователю** | личное решение: обязательства, чувства, границы, важные договорённости, неизвестная позиция | эскалация человеку |
| **Остановиться** | запрещено/нет разрешения, собеседник просит прекратить контакт, сработал стоп-фактор | не выполнять действие |

Режимы **не заменяют** обязательные ограничения, а уточняют поведение в их пределах.
Стоп-факторы (деньги, угроза, просьба прекратить, запрос обязательств/чувств) отключают
обычную автономность независимо от уровня.

### 7.2 Бюджеты автономности

Пользователь задаёт пределы самостоятельной работы: максимум сообщений за период, окна
активности, перечень знакомств с автономностью, список действий, всегда требующих
подтверждения, авто-остановка при повторяющихся ошибках, глобальная пауза.

### 7.3 Адаптивное снижение и возврат

Слой может **временно снижать** автономность при ухудшении качества ответов, нехватке
контекста или изменении условий интеграции. Возврат к более свободному режиму — **по явным
правилам**, а не потому, что модель «сама решила, что заслужила доверие». Расширение прав
из-за высокой уверенности прогноза запрещено.

## 8. Feedback & Calibration Loop (самокоррекция)

Связывает память, принятие решений и автономность. Дополняет существующий `user_feedback`.

Цикл: `Наблюдение → Классификация → Поиск закономерности → Корректировка → Проверка`.

- **Наблюдение:** ответ принят / отредактирован / отклонён / действие отменено.
- **Классификация:** фактическая ошибка · неподходящий тон · неверная стратегия ·
  личное предпочтение. (Edit ≠ плохой ответ.)
- **Поиск закономерности:** повторяется ли проблема в похожих ситуациях или единична.
- **Корректировка:** обновление предпочтения, правила выбора стратегии или оценки уверенности.
- **Проверка:** на тест-сценариях — стало ли лучше и не ухудшились ли другие случаи.

Ограничение: на первом этапе **не** дообучаем модель на каждом действии. Достаточно
управляемого обновления профиля, правил и контекстных предпочтений (дешевле, проверяемо,
откатываемо).

## 9. Данные и контракты (предложение, не финальный data-model)

Жизненный цикл памяти реализуется **локально на клиенте** в SQLite `match.db` (таблицы
`memories` и `memory_events`, схема версии 3), а не на сервере PostgreSQL (решение OQ-10).
Сервер хранит только решения агента (`agent_decisions`) и временные оценки `trust`/`compatibility`;
память не покидает устройство и не синхронизируется с сервером в Этапе 24.

Ориентир на клиенте:
- `memories(id, user_id, conversation_id?, kind, status, content, source, confidence,
  valid_until?, created_at, updated_at)` +
  `memory_events(id, memory_id, event_type, actor, detail, created_at)`.
- Статусы жизненного цикла: `received` → `classified` → `verified` → `used` → `revised`.
- Типы: `fact`, `preference`, `hypothesis`, `temporary_state`, `agreement`.
- Поля отвечают разделу 5.3 (источник, дата, уверенность, срок актуальности, история изменений,
  исправление пользователем, удаление).

Изоляция по пользователю — как сейчас; персональных данных не добавляем (ADR-0007).
Исправление/удаление памяти пользователем — обязательны; память включается в локальный экспорт
приватности и удаление аккаунта на клиенте.

Связь с Decision Loop и динамикой отношений — на Этапах 23/25+ (память кормит принятие
решений, но серверный цикл Этапа 23 пока опирается на серверные оценки риска и совместимости).

## 10. Прозрачность

Сквозная цепочка для значимого решения:
`факт → воспоминание → решение → разрешение → результат`.
Пользователь может восстановить, на каких основаниях принят шаг (см. `Decision.evidence`).

## 11. Критерии приёмки (сквозные, не только модульные)

- **Последовательность:** при одинаковом контексте/настройках агент не нарушает правила
  автономности даже при изменении формулировки входящего сообщения.
- **Память:** противоречивые/устаревшие сведения не используются как бесспорные факты.
- **Динамика:** выводы опираются на временные изменения и достаточные данные, не на одно сообщение.
- **Автономность:** запрещённые действия не выполняются даже при высокой уверенности модели.
- **Самокоррекция:** повторяющиеся ошибки дают проверяемое изменение поведения, не бесконтрольное.
- **Объяснимость:** восстанавливаются основания, использованные воспоминания, проверка
  разрешений и итог действия.
- **Безопасность:** при сомнении агент останавливается и передаёт решение человеку.

Численные пороги определяются на воспроизводимом наборе сценариев, **не** назначаются произвольно.

## 12. Порядок внедрения (предложение этапов 23–26)

Каждый этап — отдельный план, тесты, критерии и коммит (roadmap §правило).

1. **Этап 23. Decision Loop + политика действий.** Формальная модель выбора, запреты,
   условия эскалации, поведение при нехватке информации. → агент объясняет выбор/паузу.
2. **Этап 24. Memory Lifecycle.** Типы, сроки актуальности, происхождение, разрешение
   противоречий, управление памятью пользователем. → меньше повторов ошибок, гипотезы ≠ факты.
3. **Этап 25. Relationship Dynamics.** Временные ряды, поворотные моменты, сравнение периодов,
   оценка достаточности доказательств. → объяснимые изменения без поспешных выводов.
4. **Этап 26. Adaptive Autonomy + Feedback Loop.** Бюджеты, снижение автономности при ошибках,
   контролируемое обновление предпочтений. → полезнее со временем при сохранении контроля.

## 13. Открытые вопросы (новые, к закрытию владельцем)

- **OQ-9.** Формальная модель уверенности и пороги эскалации (какие значения и на каком наборе).
- **OQ-10.** Где живёт память: сервер (PostgreSQL) и/или локально (SQLite клиента, ADR-0022),
  и как синхронизируется при оффлайн-очереди (ADR-0026).
- **OQ-11.** Формат и хранение временных рядов динамики; политика устаревания сигналов.
- **OQ-12.** Пороги бюджетов автономности по умолчанию и правила автоматического возврата.

## 14. Не-цели

- Манипуляция собеседником, скрытые проверки, провокация ревности.
- Автономное расширение прав агентом.
- Незаметное превращение единичного поведения в устойчивую черту личности.
- Дообучение модели на каждом действии пользователя на первом этапе.
