## P0-1. «Автономность ≠ автономная работа на площадке»

**Статус: подтверждено, но это документированное архитектурное решение (ADR-0004/0008,
не дефект реализации)**

Факт: конечного адаптера знакомств нет — `IntegrationRegistry` содержит только
`ManualImportAdapter` и заглушки `UnsupportedAdapter` (tinder/badoo/bumble/okcupid/hinge/mamba).
`services/api/app/integrations/base.py` (строки 1–6) прямо фиксирует: агент не подключается
к площадкам напрямую, наблюдает экран через Vision. Цикл «увидеть → подготовить ответ →
отправить → проверить результат» требует автоматизации ввода (клики/клавиатура) — она
в v0.1.0 не реализована и объявлена вне релиза.

**Что сделано:** требование честно зафиксировано как открытый пункт; в отчёте о релизе
явно указано, что автономность = внутренний контур (решения, бюджет, доставка в оффлайн-очередь),
а не непосредственное взаимодействие с сайтом знакомств.

## P0-2. «Безопасное поведение автоотправки не испытано целиком»

**Статус: механизмы есть и покрыты unit-тестами; сквозной (API-e2e) набор
чувствительных сценариев отсутствовал — доделано**

Факты (до работ):
- stop-факторы: `decision/policy.py` `decide()` шаги 1–3 (риск `warn_and_pause` → STOP;
  чувства/обязательства → ESCALATE; пауза/не-auto_send → VERIFY).
- risk-паттерны: `trust/engine.py` — `financial_request` (деньги/крипта/реквизиты),
  `personal_data_request` (карта/CVV/паспорт/код из смс), isolation, urgency.
- идемпотентность: `POST /api/v1/agent/actions` — повтор с тем же ключом возвращает
  то же действие (`tests/test_agent.py:111`).

Дефект: scenarios «ошибочный анализ / неоднозначное сообщение / просьба о деньгах /
личные данные / чувства и границы / повторная отправка после сбоя» проверялись только
на уровне unit-политики (`tests/test_decision.py`), а не полного пути через API.

**Что сделано:** `tests/test_safety_autonomous.py` — сквозные сценарии через реальный
API (создание знакомства в auto_send → импорт входящего → evaluate/действие):
деньги, личные данные, «давай только мы», неоднозначное сообщение, повторная
отправка с тем же idempotency-key (без дубля).

## P0-3. «Приватность описана слишком категорично»

**Статус: подтверждено — заявление расходится с моделью данных; доделано**

Факт: README:12 и `docs/security/security-review.md:12,30` заявляют «персональные
данные не собираются». При этом модель данных содержит: тексты сообщений обеих
сторон (`Message.content`), профиль целей/ценностей (`UserProfile`), стиль общения
(`CommunicationProfile`), память, оценки риска и совместимости. Промпт LLM
(`app/dialogue/context.py`) включает ВЕСЬ цитированный текст переписки (в
fencing-маркерах), описание стиля пользователя и его цели — то есть при облачном
провайдере (`openai` + пресеты groq/gemini/openrouter/cerebras) эти данные
покидают машину. Резервная копия PG (`scripts/backup_pg.ps1`) содержит все
серверные данные целиком.

**Что сделано:** новая политика `docs/privacy/privacy-policy.md`: матрица «что где
хранится», что уходит провайдеру, сроки хранения, удаление, состав резервных копий;
формулировки README/security-review приведены к фактическому положению.

## P1-1. «Настройки LLM могут вести себя неожиданно»

**Статус: подтверждено (частично); доделано индикацией и проверкой**

Факты: `.env.example` — echo + `MATCH_LLM_USER_REQUEST_LIMIT=0`; активный провайдер
и статус fallback не surfaced в API (`provider_names` был только внутренним в
`LLMGateway`); в UI нет явного индикатора «модель/провайдер/готовность».

**Что сделано:** `GET /api/v1/llm/status` — текущий провайдер, цепочка fallback,
факт пропуска за неналичием ключа, лимит на пользователя (0 = выключен) — с тестами;
`.env.example` — явные предупреждения у дефолтов; UI: секция «Языковая модель» в
«Настройках» (`lib/llmStatus.ts` + `lib/llmStatus.test.ts`, 4/4) показывает провайдера,
fallback, пропущенных и лимит; устаревшая подсказка про «не собираются» исправлена.

## Что НЕ является дефектом (по результатам аудита)
- Отсутствие адаптера площадки — ADR-0004/0008, документировано.
- Автономная доставка ≠ отправка на сайт: это внутренний контур очереди/бюджета.
- echo-провайдер по умолчанию — сознательный оффлайн-дефолт, задокументирован.
